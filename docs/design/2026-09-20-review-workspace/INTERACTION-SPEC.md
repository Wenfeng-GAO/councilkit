# CouncilKit 审查工作台：交互与数据契约

日期：2026-09-20。源码核对基线：`3f968a2`。范围：`kind=review` 的报告详情、席位详情、实时与历史过程。本文是交付给前端 Agent 的设计要求，**不是现状功能清单**；新增能力都在下文标注。与同目录高保真画面配套，以本文规定状态含义、数据来源及交互边界。

## 1. 设计目标与边界

- 进行中，首先回答“目前在做什么、多久没有新活动、哪些席位已经有结果”。
- 完成后，首先回答“结论是什么、有哪些发现、依据在哪里”，再提供完整报告与历史过程。
- 本轮审查结果与当前修复进展分开；每项结果绑定 Run 和被审查的提交，不随修复过程改写含义。
- `success` 表示执行成功，不表示审查通过；没有发现、没有结果、无法解析是不同状态。
- 单席意见是独立结果，Aggregator 才提供本轮汇总结论；不把投票多数当作正确性证明。
- 沿用 Council / Reporter / Run / Autonomous Run / Attempt / Aggregator 等项目术语。席位是界面称呼，持久化身份使用 `attemptId`。
- 不改 `kind=squad` 的只读观察契约，不给 squad 增加修复、复审或结果裁决入口；不将本文的审查结论解析用于 ideate。

## 2. 信息结构

### 2.1 报告详情页

1. **上下文头部**：PR 标题与链接、Run 标识、审查提交 SHA（缺失则明确“提交信息缺失”）、执行状态。职责名称在前，模型与 Driver 在次级信息中。
2. **本轮审查**：汇总结论、已有证据支持的发现数与阻塞数、覆盖情况、阅读汇总报告入口。Aggregator 尚未完成时显示“等待汇总”，已完成席位结果仍可立即打开。
3. **当前修复进展**：仅有 `pipeline` 时显示，独立面板展示阶段、修复轮次、更新时间与实际可用的后续复审链接。不复用“5 / 5 审查席位已结束”作为修复进度。
4. **席位列表**：紧凑、稳定排序，展示职责、执行状态、结果摘要/当前活动、时长和入口。完成后“查看结果”；运行中“查看进展”；失败“查看详情”。
5. **发现与汇总报告**：结构化发现用于筛选与阅读；原始报告始终可读。完整性警告放在结论旁，不能埋在页尾。

“轮次”只显示真实 `pipeline.round` 或服务端明确返回的版本关系。`againstRunId` 是关联 Run，不是可以任意加一的显示轮次；没有完整链时用“本轮 / 上轮 Run”，不编造“第 3 轮”。

### 2.2 席位详情

- 采用可展开为大阅读区的详情面板。头部固定包含席位职责、执行状态、模型次级信息、执行版本与关闭按钮。
- 顶部导航可切换席位；职责相同才显示必要的模型或短身份作为区分。
- 首次打开已结束席位：**结果摘要 → 发现（有可靠结构化数据时）→ 完整席位报告 → 历史过程**。
- 首次打开运行中席位：**当前活动 → 最新过程**；结果未生成时不占据大面积空白。
- 页面已经处于历史阅读时，完成事件只更新状态并展示“结果已就绪 · 查看结果”，不替换面板、不切换 Tab、不滚动、不自动收起过程。
- “历史过程”保持可访问。若过程不存在而结果存在，结果仍完整展示。
- 汇总席位明确标注“Aggregator / 汇总报告”，不能混成又一个独立审查意见。

### 2.3 操作语义

- “重新读取结果/过程”只重发读请求，不重新执行 Agent。当前 Host actions 只提供 `fix` 和 `re-review`；不能给“重试失败席位”接上 `re-review` 冒充单席重试。
- 如果设计画面出现单席重新执行入口，该入口需另行补齐 resume/重试语义与接口后启用；P0 采用现有可用动作，按钮文案与执行范围一致。
- “立即修复/重新审查”等执行动作沿用现有流程与权限边界；本设计不引入新的后台任务。Host 不可用只提示连接状态与恢复方法，不自动拉起 Host。

## 3. 状态矩阵

状态分三条独立轴：**执行状态、结果可用性、过程可用性**。不能用一个绿点覆盖三个含义。

### 3.1 席位执行与结果

| 事实条件 | 主状态文案 | 首次打开位置与内容 | 行为与限制 |
| --- | --- | --- | --- |
| `pending` | 等待启动 | 等待说明；若为 Aggregator，解释等待席位结果 | 不运行计时，不显示虚构队列名次 |
| `queued` | 排队中 | 排队说明 | 无真实时间戳时不显示排队时长/预计开始时间 |
| `running`，尚无 live 事件 | 进行中 · 等待首条记录 | 当前活动区域与等待态 | 无记录不等于卡死；显示已有执行时长 |
| `running`，有事件 | 进行中 | 当前活动与最新过程 | 展示最近活动时间；不显示推测完成百分比 |
| `running`，一段时间无新事件 | 进行中 · 最近活动 N 秒/分钟之前 | 保留已读过程 | 文案“暂时没有新记录”；不得自动改为失败/卡死 |
| `success`，结果请求尚未返回或落盘尚未可读 | 执行完成 · 读取结果中 | 结果骨架与保留的过程 | 这是加载态，不能宣称通过；短暂重试后转明确不可用状态，避免无限“处理中” |
| `success`，正文存在但结构化解析失败 | 执行完成 · 结果未解析 | 原始 Markdown 正文优先 | 不输出 `0 项发现`，不暗示稍等就会自动解析；允许阅读、复制原文 |
| `success`，权威正文缺失/空输出 | 执行完成 · 暂无结果正文 | 空态与过程入口 | 无输出不等于无问题；保留执行成功的真实事实 |
| `success`，可靠结构化结果有发现 | 执行完成 · N 项发现 | 结果摘要、发现、报告 | 严重性与计数来自确定的数据源，不从过程文本猜测 |
| `success`，结构化结果明确零发现但无明确 verdict | 执行完成 · 未列出发现 | 结果摘要与报告 | 不升级为“通过审查” |
| `success`，可靠结果明确 `approve` | 独立意见：通过 / 汇总结论：通过审查 | 结论与报告 | 单席明确独立意见；不得覆盖缺席/结果不完整提示 |
| `success`，可靠结果明确 `changes-requested` | 独立意见：需要修改 / 汇总结论：需要修改 | 结论与发现 | 仍可显示执行完成；结论颜色不能反向改变执行状态 |
| `failure` | 执行失败 | 失败原因、最后已记录活动、历史过程 | 区分执行错误与“需要修改”；无错误细节时明确“未记录详细原因” |
| `cancelled` | 已取消 | 取消状态与保留的过程 | 不显示“审查失败”或生成结论 |
| 不认识的旧状态或数据缺失 | 状态未知 | 已有报告/过程仍可读 | 不猜测已完成、不补默认通过 |

当前 `CliRunAttemptResult` **没有 verdict 字段**，`parseStatus=parsed` 只代表现有摘要器识别了特定标题或严重性文本，不能作为上表“可靠结构化 verdict”的来源。P0 对单席默认使用“执行完成 / N 项发现 / 结果未解析”等保守文案；“通过 / 需要修改”只在明确来源满足契约后启用。

### 3.2 过程与读取状态（可与任意执行状态叠加）

| 过程状态 | 展示 | 后续交互 |
| --- | --- | --- |
| 首次读取中 | 小型骨架或“正在读取过程” | 不清空已经存在的结果 |
| 运行中无记录 | “等待首条记录” | 继续轮询 |
| 已结束无记录 | “未保存过程记录” | 保留结果；不能显示“审查未运行” |
| 明确截断事件 | “过程记录已截断，当前展示已保存内容” | 若 `dropped` 是累计值，按协议去重/取最新，不能随意相加；不以截断片段推导最终结论 |
| 请求失败且有缓存 | “过程读取失败，已保留读取内容” | 自动重试期间可继续阅读；保留游标与滚动位置 |
| 请求失败且无缓存 | “过程暂时无法读取” | 显示“重新读取”；不等同无记录 |
| 结果读取失败 | 结果区显示可重试错误 | 历史过程保持可用，不从 live 猜一个结果作为替代 |
| 报告正文受读取上限截断 | 结果区明确“正文未完整加载” | 提供后续加载/全文读取能力后才能给出全文搜索或完整性承诺 |

注意：现有 Host `readLiveSidecar()` 将缺失、部分文件系统错误都退化为 `[]`，API 目前不能完整区分“未保存”和“文件读取失败”。前端只能准确展示 HTTP/网络失败；文件级区别需要 P1 接口元数据支持，不能假装已获得。

### 3.3 页面级结论

| 情况 | 页面主信息 |
| --- | --- |
| 部分席位完成、其余运行 | “审查进行中 · X / Y 席已结束”；已完成席位可看结果；Aggregator 显示等待/运行真实状态 |
| 所有席位终态、Aggregator 运行 | “正在汇总”；不是“审查通过”，不把席位计数当成整个流程百分比 |
| Aggregator 完成但结果未解析 | “审查执行完成 · 汇总报告待读取/未解析”；已有正文可直接阅读 |
| 有失败/缺席，仍有汇总报告 | 显示汇总结论，并相邻显示“结果不完整 / N 席未完成”；不隐藏降级事实 |
| 审查完成，同时 pipeline 活跃 | “本轮审查：需要修改”等历史结论 + 独立“当前修复：正在起草修复方案”等活动信息 |
| 修复声明已成功，尚未验证 | “声明已修复 · 待验证”；不能显示“已解决” |
| 旧报告绑定旧 SHA | 明示审查 SHA；仅有新修复状态不能宣称当前提交已通过 |

## 4. 实时跟随、完成切换与阅读连续性

1. 首次打开运行中席位默认跟随底部。滚离底部即暂停跟随；按钮状态及屏幕阅读器提示同步更新。
2. 暂停后，新记录在内存追加，显示“新增 N 条活动 · 回到最新”。N 统计稳定活动行/分组，而非 token delta；不能每个字符都加一。
3. 用户选择“回到最新”才恢复跟随。顶部固定条与浮动条不能遮挡最后一条内容。
4. 同一席位完成后，当前阅读位置与展开状态不变。显式“查看结果”再跳转结果区。首次重新打开已完成席位才默认结果优先。
5. 席位切换按 `runId + attemptId + executionRef` 保存视图状态：模式、查询、筛选、展开组、锚点和组内偏移。恢复时先定位稳定活动锚点，避免新事件插入造成位置漂移。
6. 结果较长或 Markdown 重新排版时，使用稳定区域高度/滚动锚点；不能因结果插入在过程前面导致历史阅读跳动。
7. 关闭后回到触发入口，键盘焦点不能丢失。关闭按钮、Escape、席位 Tab、搜索与折叠区域均可键盘操作；模态模式管理焦点，非模态布局不得伪装为模态。
8. 网络恢复只续取游标后的数据。以稳定版本和序号去重，不重复追加旧活动；切换席位后的迟到响应必须忽略。
9. 活动时间使用真实事件时间或明确 heartbeat 字段。进度文件 `updatedAt` 不能被误称为“Agent 最近输出”；时间戳不可解析则隐藏相对时间并提供“时间未知”。

## 5. 历史过程：分组、摘要和搜索

### 5.1 默认阅读层级

- 层 1：Agent 已记录的进展文本、进行中的工具活动、结果就绪节点、读取/截断提示。
- 层 2：连续同类工具活动，例如“读取 6 个文件”“搜索 3 次”“执行 2 条命令”。点击展开原始时间、路径/命令和状态。
- 层 3：原始事件文本与已有思考记录；默认折叠，保留读取入口。空摘要工具归入“无详情的工具活动 N 次”。

P0 分组只用真实事件类型、工具类别与先后顺序，不调用模型补写阶段。不可把一串 `read_file` 自动命名为“已完成安全验证”。阶段标签只有来源明确提供时才显示。

### 5.2 确定性分组规则（建议，待实现）

1. 先按服务端序号重放并折叠连续 `text.delta` / `thinking.delta`；相同序号去重。
2. 相邻同类别且已完成的工具行可合并；在进展文本、进行中工具、截断边界、执行版本边界处断组。不跨席位/版本合并。
3. 每组使用第一条源事件序号作为稳定 ID；展示起止时间、工具调用次数与有限路径预览。“6 次读取”与“6 个文件”区别：只有可确认不同路径数时才说“文件”。
4. 同一路径重复读取保留次数，不去掉“冗余”证据；同一命令多次执行也不能当成一次。
5. 当前 live 事件没有 `toolCallId`、工具输出正文或可靠 exit code。允许显示“调用结束”，**不得将 `tool.completed` 渲染为‘测试通过’**。同名并发工具不能精确配对时保持独立记录，不创造精确耗时。
6. 被截断的摘要显示省略，复制操作只能复制实际保留文本；不得把 240 字摘要称为“完整命令”。

### 5.3 搜索与筛选

- 输入框提示“搜索已保存的过程、路径或命令”；范围固定为所选席位和执行版本。
- 文本搜索默认大小写不敏感，按字面量匹配，不执行用户输入的正则；保留中文、路径和命令字符。
- 类型筛选：全部 / 进展 / 工具 / 思考。筛选和搜索用 AND 组合；类型计数基于折叠后的活动，不基于增量 token 数。
- 命中折叠组时展示命中数，定位时只展开该组并高亮匹配文字；不把一整组不相关记录当成命中。
- “无匹配结果”与“没有过程记录”不同；提供清空筛选。清空搜索后恢复此前展开与滚动状态。
- 搜索范围不含服务端没保存的内容或工具输出，不承诺完整执行日志。出现截断时相邻提示“仅搜索已保存部分”。
- 暂停跟随时新的匹配只更新结果计数，不抢焦点、不重新定位当前命中。
- P0 在当前接口实际返回的保存范围内做本地检索；如未来分页，必须标明“已加载部分”并提供加载剩余记录，未加载完整前不得声称全量搜索。

| 多席位对同一发现的完整立场 | `source/reviewer` 与部分 group/adjudication | 不能可靠推导每个席位支持/反对矩阵；完整关联属 P1 新契约 |
| 结果深链、执行版本选择、过程检索 | 尚无完整能力 | 设计建议，需实现与验收 |

### 6.1 P0 必需：按执行版本读取持久化席位结果

建议接口（名称可由实现者调整，语义必须满足）：

```text
GET /api/v1/cli-runs/:runId/attempts/:attemptId/result
GET /api/v1/cli-runs/:runId/attempts/:attemptId/result?executionRef=<opaque-ref>
```

建议返回语义，不要求另造独立数据库：

```ts
type AttemptResultResponse = {
  runId: string;
  attemptId: string;
  executionRef: string; // 服务端从持久化记录定位的稳定、不透明标识
  executionStatus: "pending" | "queued" | "running" | "success" | "failure" | "cancelled";
  availability: "pending" | "available" | "empty" | "unavailable";
  markdown: string | null;
  truncated: boolean;
  summary: CliRunAttemptResult | null; // 现有保守摘要，可复用
  failure: { code: string; message: string } | null; // 已记录、可展示的错误
  versions: Array<{ executionRef: string; label: string; status: string }>;
};
```

约束：

- 唯一身份不能只用 `agentName`、模型或 `attemptId`。现有重试记录含可选 `attemptNumber/retryOf`，`review.resumed` 还会再次复用同一个 `attemptId`；所以还需区分 resume 代次或稳定记录位置。`attemptNumber` 单独也不够。
- 服务端顺序解释 durable transcript：首次运行 → 重试 → resume。当前代次被重新执行的席位必须显示当前状态，不允许 fallback 到上一次成功正文；显式 `reusedAttemptIds` 才能复用历史成功版本，并标注来源。Aggregator 每次 resume 都重新运行。
- 可由版本化的 transcript 记录引用/稳定记录索引生成 `executionRef`，无需 P0 重写历史文件。但该标识需能在原子重写后仍定位同一条记录，并在后续 append/resume 后保持语义稳定。
- 浏览器默认打开当前执行版本；历史版本只有显式选择才展示。选择后标题和 URL/状态标明“历史执行”，不能混入当前结论。
- 原始正文来自准确匹配的 `attempt.finished.output` / `aggregation.finished.output`，不从 live 正则提取，不取“最后一段超过 280 字的文本”，不以“最后一次成功”覆盖后来的失败。
- 现有目录摘要扫描有读取上限；新接口必须能读取目标完整记录或明确返回截断/不可用，不将 cap 之外的记录视为不存在。
- 原子写入与请求竞态可能造成短暂结果未就绪；使用 `pending` 区分。持久化空输出或解析失败要进入确定状态，不持续加载。
- 严格验证 Run、Attempt 和版本，沿用 session 认证、目录边界与非符号链接规则。未知版本返回可诊断错误；损坏记录不能回显原始敏感行。
- 保留 Markdown 安全渲染方式；不得将正文作为 HTML 直接注入。错误面板仅展示已净化的错误字段。
- 旧版 live 文件只有 `attemptId`，未必能定位历史执行版本；无法证明过程与版本一致时，历史结果下展示“此版本的过程未单独保存”，不得附上当前版本过程充数。

### 6.2 P1 才启用的能力

- 明确的单席结构化 verdict、逐条 finding 和解析版本；优先来自稳定结构化产物或严格解析 durable output，不能继续扩大 live 正则猜测。
- 每条发现的席位出处、采纳/驳回理由、证据指针，绑定 `runId + SHA + attemptId + executionRef`。缺数据就隐藏立场矩阵与精确证据跳转。
- live 响应增加可选读取元数据（缺失/不可读/坏行/截断）、执行版本、工具调用 ID；精确工具配对、可靠调用耗时、历史执行过程和完整日志读取依赖这些字段。
- 真实阶段事件（如“验证中”）需要生产方发出；本地分组仅做活动分类，不能创建语义阶段。

## 7. 交付分期与依赖

| 优先级 | 前端交付 | 后端/数据依赖 | 完成标准 |
| --- | --- | --- | --- |
| P0-A | 审查与修复分区、完成列表紧凑化、职责标签、执行/结论分离 | 现有 detail/progress/pipeline/report | 不新增任务执行行为，所有缺值均有准确退化文案 |
| P0-B | 完成席位结果置顶、完整报告、历史版本标识、读取异常态 | **必须新增 durable result 读取与版本选择语义** | 无 live、live 截断、重复 attemptId、失败重试仍取对正文 |
| P0-C | 当前活动、暂停跟随、新活动提示、结果就绪不打断阅读 | 现有 live；可选 heartbeat 字段 | 完成/轮询/切换均不抢滚动与焦点 |
| P0-D | 同类活动分组、本地搜索/筛选、展开阅读 | 现有保存范围内数据即可 | 计数正确、时间序不变、范围文案准确；不承诺工具输出全文 |
| P1 | 结构化席位发现、意见关系与证据定位 | 新结构化结果/关联数据 | 每个关系可追溯，缺席不等于反对，旧 SHA 不冒充当前结果 |
| P1 | 可靠执行版本过程、工具精确耗时与文件级错误区别 | live 协议/持久化升级 | 保持旧记录可读，旧数据缺失时可退化 |

P0-B 不能以静态 mock 接完就宣称完成。开发可以并行推进外观，但验收时必须使用真实 durable result 数据；未上线的 P1 元素不得显示虚构计数、按钮或关系。

## 8. 验收案例

| 场景 | 操作 | 应观察到的结果 |
| --- | --- | --- |
| 5 席中 1 席完成、其余运行 | 打开已完成席位 | 无需等待 Aggregator，先见该席完整 durable 报告；独立意见标识明确 |
| 成功执行但输出普通自然语言 | 查看结果 | 展示原文和“结果未解析”；不出现 0 发现/通过标记 |
| 正文明确零发现但无 verdict | 查看结果 | “未列出发现”，不转换成通过 |
| 执行失败但 live 末尾含“approve” | 查看详情 | 显示失败；结果不从 live 提取，不显示通过 |
| 过程未保存，最终正文完整 | 打开完成席位 | 结果完整；过程只提示未保存 |
| 2 MB 过程达到上限 | 搜索与看结果 | 截断提示存在，搜索仅保存部分；最终报告仍来自 durable 结果 |
| 用户滚到历史中部时席位完成 | 等待状态轮询 | 滚动、焦点、展开状态不变，出现“结果已就绪”；点击后才跳转 |
| 暂停跟随后持续 token 流 | 等待并切换筛选 | 按稳定活动计数，无每字符增长；不自动滚动 |
| 同一个 attemptId 先失败后重试成功 | 打开默认结果，再选历史版本 | 默认显示本次成功；历史可看失败事实；版本身份不冲突 |
| resume 再跑同席，旧版本成功但当前仍运行/失败 | 打开当前结果 | 不展示旧成功为当前结果；显式复用的席位才标注复用 |
| 快速 A → B 切席，A 请求后返回 | 等待请求完成 | B 内容不被 A 覆盖；切回 A 保留其阅读位置 |
| 读取错误后恢复 | 断开请求后重试 | 保留已有记录；按游标续读，无重复活动；结果读取错误不污染过程 |
| 目标 transcript 记录超过现有摘要读取范围 | 打开席位报告 | 能取到目标全文或明确截断；不伪装成空结果 |
| 同名工具并发且完成顺序交错 | 展开组 | 不展示无法证明的配对、耗时或“验证通过” |
| 原审查已结束且修复进行中 | 查看页面首屏 | 分别看到原结论与当前修复阶段；审查计数不冒充修复进度 |
| 修复声明成功但无验证证据 | 查看发现 | “声明已修复 · 待验证”，不标为已验证解决 |
| 带 HTML/脚本的输出或异常长路径 | 阅读/复制/搜索 | 安全渲染，无脚本执行，布局可换行，复制不声称超出已存摘要 |
| 键盘与窄屏阅读 | 用 Tab/Enter/Escape 打开切席关闭 | 操作可达、焦点可见、关闭后回源入口，无横向溢出或遮挡主要操作 |

验证以真实行为和关键状态为主；重点覆盖版本映射、失败/缺失语义及滚动连续性，不为每个静态样式写实现镜像测试。
