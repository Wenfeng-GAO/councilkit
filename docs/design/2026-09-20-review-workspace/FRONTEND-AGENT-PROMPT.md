# 给前端 Agent 的实现任务

请在当前 CouncilKit 仓库中实现审查报告与席位体验的改版，严格按照 `docs/design/2026-09-20-review-workspace/` 的设计包工作。目标是让用户在执行中快速辨识当前动作，在单席完成后立即读取结果，在需要时高效回看过程。

## 必读材料

1. 仓库 `AGENTS.md` 与本地当前改动；不得覆盖其他任务的文件。
2. 本设计包 `README.md`、5 张 `screens/*.png`、`VISUAL-SPEC.md`、`INTERACTION-SPEC.md`、`design-tokens.json`。
3. 当前实现：`src/app/pages/ReportDetailPage.tsx`、`src/components/report/`、`src/lib/live-transcript.ts`、`src/styles/report.css`、`src/styles/review-live.css`；数据约束参照 `shared/runtime/` 与 `runtime-host/routes/cli-runs.ts`。文件若已重构，以当前代码为准。

先实际打开图片再实现，不要只读文件名或照文字猜布局。图片定义视觉层级；交互规格定义行为与数据语义；tokens 定义尺寸和颜色。发生矛盾时按 README 的优先级处理，并记录必要调整。

## 需要交付的用户体验

- 完成的 Run 采用结果优先的总览：结论、优先问题、紧凑席位列表、完整报告。
- 已完成席位默认展示结论摘要、可用的结构化发现、完整报告；历史过程在下面。没有结构化解析时显示原始正文与明确状态，不能猜成通过或零问题。
- 执行中采用席位列表 + 当前动作 + 最新过程。已完成席位可随时打开；Aggregator 尚未完成时明确标注独立意见。
- 实时过程支持显式暂停跟随、新增活动数量、回到最新。用户正在看历史时完成事件只提示结果就绪，不切换页面或滚动。
- 历史过程支持确定性分组、已保存文本/路径/命令搜索、类型筛选、展开明细、保留每席位阅读状态。
- 历史审查结果与当前修复进展分区，Run/SHA/轮次均来自真实数据；不能把旧席位完成数当作新修复进度。
- 使用正式视觉规格的响应式与可访问性规则，保持桌面长文阅读清楚，在 390px 宽度可用。

## 实现边界

- 本包是设计提案，不代表截图中所有能力已实现。请核对当前代码再规划差异，复用已有结果面板、读取错误处理与跟随逻辑，避免重复实现。
- **结果来源必须可靠**：按 `runId + attemptId + executionRef`（或能证明等价的版本键）读取 durable transcript 对应 `attempt.finished.output`。当前 UI 的 live 正则和 240 字摘要不能满足完整报告要求。补齐最小必要 Host 只读接口或等价契约；不要用前端假数据掩盖接口缺口。
- demo 中单席 `需要修改` 要求有明确 verdict 来源。若接口没有，不得从 `success` 或严重度关键词推导 verdict；降级为“执行完成 · N 项发现 / 结果未解析”，正文仍可读。
- 工具调用结束不等于测试通过；没有明确 exit code / 检验结果时不能显示成功测试状态。
- 没有真实 API 的功能不得做空按钮。精确证据跳转、采纳关系、单席重新执行属于另行补齐能力的范围；按 VISUAL-SPEC 处理展示。
- “开始修复”沿用已有 fix 的执行范围；明确动作可能修改代码并 push。不得新增自动启动修复、自动拉起 Host、自动运行审查等副作用。
- 保留 `kind=squad` 的只读观察边界，保留 ideate 等非 review 页面，不能把 review verdict 强行套到所有 Run。
- 不重写 CLI 与 Runtime Host 通信架构，不改 `src/runtime/client.ts` / `event-stream.ts` 的项目受保护路径，除非另有明确授权。
- 仅修改本任务相关文件，不自动提交、推送、部署或创建 PR。

## 工作顺序

1. 检查现有实现与设计差异，列出所需最小数据变化，确认可以可靠读取单席最终正文。
2. 先完成结果优先、执行与结论分离、修复分区和非打断实时跟随；随后做过程分组搜索、阅读状态保留和响应式。
3. 使用确定性 fixture 覆盖 5 张设计状态，以及缺失正文、未解析、失败、中断、读取失败、截断和部分完成。
4. 跑与改动相关的类型检查、测试和 lint；用浏览器截图核对 1440、1024、390 三种宽度。对照截图检查层级、间距、字号、换行、溢出和焦点。
5. 根据 INTERACTION-SPEC 的验收案例验证行为，尤其是单席先完成可读、完成时不打断阅读、迟到响应隔离、错误保留已读数据。
6. 最后说明实现了什么、怎样验证、有哪些确实未实现的数据依赖；不要把设计截图冒称为应用测试截图。

## 验收底线

界面可真实操作、状态由真实数据驱动、旧记录可读、结果不依赖 live 存在、无未知即通过、无运行过程抢滚动、无无效操作入口。不能只实现一张静态截图就宣称全部完成。
