## 总体判断

**支持“由确定性控制器管理目标、预算与准出”的方向，但建议修改后再实施 v2。最值得优先解决的不是增加审查角色，而是让“裁决、执行、证据、准出”使用同一套权威状态。**

现方案已经明确了不少正确边界，包括不把预算耗尽当成功、不让 Builder 自行降低验收、隔离候选测试与发布权限，以及要求合格候选能够通过。我的主要意见不是再添加一层平台，而是把这些原则收敛成可执行的规则。

本次是对附件中控制协议及实现摘录的独立评审，**不是对 PR #128 当前源码的准出判定，也没有复跑附件中的测试。**

## 一、五个高置信度问题

### 1. 修复策略 hash 还不够：准出装配存在把“未知”变成“肯定”的路径

**类型：当前实现摘录可确认的契约问题；真实入口可达性仍需验证。**

**原文依据**

终验调用处不仅使用固定 `POLICY`，还包含：

```typescript
!remote.baseSha
prOpen: remote.prOpen !== false
```

前者可以使缺少远端 base SHA 时的 `baseUnchanged` 成为 `true`；后者把未提供的 PR 开放状态也当作开放。与此同时，合法的 Squad 策略 hash 又不能与固定字符串 `gate-policy-1` 相等。:chatgpt-content-reference{index="3"} :chatgpt-content-reference{index="4"} :chatgpt-content-reference{index="5"}

**失败轨迹**

构造一个候选 `C`，其测试与审查均合格，远端 source HEAD 也确实是 `C`，但 adapter 没有返回 `baseSha` 和 `prOpen`：

1. 修复 hash 不一致后，Squad 条件可以通过。
2. 装配层把缺失的 base 证据转换成“base 未变化”。
3. 把缺失的 PR 状态转换成“PR 仍开放”。
4. 后续 gate 收到的是两个肯定布尔值，已经无法区分“核验成功”和“根本没拿到证据”。

**从摘录能确定的是第 2、3 步的转换；材料不足以证明完整入口一定允许这些缺失值到达此处。**但这已足以要求修正装配契约，而不能只补一个 hash 测试。

**最小修正**

终验所需的身份事实必须采用“明确证实才通过”的规则：未知、缺字段、读取失败与不匹配分别保留原因，不能预先压成 `true`。

策略 hash 必须来自控制器事先冻结的可信策略。**不能简单把候选返回的 hash 同时用作 expected hash，否则比较会退化成自我相等。**

`publishedSha ?? identitySha` 也宜改成真实交付记录；远端原本已经是该候选时，可以明确记录一次“核验后采用现有远端候选”，而不是补出一个未实际取得的发布字段。:chatgpt-content-reference{index="6"}

**验收**

必须经过生产装配路径验证：合法候选能够通过；未知或不同策略不能通过；缺少必需的 base/PR 状态不能通过；远端已经是合法候选的无须推送路径能够通过。不能只向 `evaluateRepairGate` 手工传入理想输入。

### 2. “发现裁决”尚未明确成为准出权威，仍可能被原始账本重新否决

**类型：提案与既有账本行为之间的衔接缺口，影响误阻塞和重复修复。**

**原文依据**

R2 规定，原始 finding 是待裁决发现，控制器只派发经裁决且在范围内的修复；R8 又要求继续满足现有 finding 准出规则。现有摘录中，任何 `still_open` 回执都能重新打开记录，匹配到的文字发现也能阻止关闭。:chatgpt-content-reference{index="7"} :chatgpt-content-reference{index="8"}

最新聚合报告还明确出现了“原反例已消失，但用同一 ID 改记新症状”的做法。这不意味着新反例应被删除，却说明“ID 稳定”不等于“被验证的断言稳定”。:chatgpt-content-reference{index="9"}

**失败轨迹**

1. 原断言 `E1` 在候选 `C` 上已有有效关闭证据。
2. 新报告使用相同 ID 描述另一条反例 `E2`。
3. 裁决者认为应保留 `E1` 的验证结果，并单独处理 `E2`。
4. 旧账本仍因该 ID 存在 `still_open` 或匹配文本而把整项重新打开。
5. 进展统计再将它解释为“旧问题又修失败了一次”。

结果是：**裁决可能改变“接下来修什么”，却不能改变“最后依据什么准出”。**即使前面的语义裁决正确，控制器仍可能持续误阻塞。

当前 `sameAgainstStillOpen` 只比较正常的 against 链关联，并未比较根因；`stillOpen` 又包含所有非 accepted 记录。这会进一步混淆真正失败、历史关闭和缺证据。:chatgpt-content-reference{index="10"} :chatgpt-content-reference{index="11"}

**最小修正**

建立**一份经裁决的验收清单**，派工、进展判断和准出都读取它，而不是各自解释原始账本。

每项至少固定“断言版本、违反的不变量、反例/证据引用、原始 ID 映射”。新反例可以补充同一不变量，也可以形成新的关联项，但不能静默替换旧断言。根因分组可以调整，历史验证对象不能随之被改写。

这不意味着放松全部非有效 accepted 项闭环的要求。重复项必须有可核对的等价映射；被证伪项必须有独立证据；尚未复现不等于证伪。**如果旧 gate 无法表达这些结论，就需要显式修改其输入协议，不能一边保留原始文字的无条件否决权，一边声称裁决已生效。**

**验收**

旧断言关闭、新反例成立时，两者均被正确记录，不误计为旧断言再次失败；别名不增加根因数量；两个不同新根因不触发“同根因两次”；未评估不制造事实冲突，但缺少必需责任覆盖仍不能通过。

### 3. 真实回执不等于有效验收：必须绑定实际受测内容和测试所证明的断言

**类型：证据协议需要补成可执行规则，而非否定 R3/R8 已有方向。**

**原文依据**

R3 要求保存坏版本失败、新版本通过的对应证据；R8 要求执行器直接采集命令、退出码、日志、SHA 和测试版本。方向正确，但材料同时给出了一个关键反例：测试在 `Eventually` 中再次调用 Retry，因而不能证明系统会自行恢复。:chatgpt-content-reference{index="12"} :chatgpt-content-reference{index="13"}

**失败轨迹**

即使完全消除了手写 stdout，仍可能出现：

- 命令真实执行并返回零，但没有运行到要求的测试，或者测试被跳过。
- 测试真实通过，但通过原因是测试额外调用 Retry，主动修复了被测状态。
- 回执记录 `HEAD=C`，实际运行目录却含未声明的修改、辅助测试或替换文件，验证对象并不只是提交 `C`。
- 历史坏版本确实 FAIL，但失败来自编译或环境问题，而不是被声称修复的不变量。

因此，**来源真实、候选身份真实、验收含义正确，是三个不同条件。**

**最小修正**

每个必需验收项增加一条很短的可观察定义：

> 在哪些前置条件下，施加什么触发，允许测试随后做什么，观察什么结果，哪些环境假设成立。

例如，Ready 自恢复测试可以释放事先设置的 barrier、观察状态，但不能通过再次调用 Retry 来完成恢复。断言应针对外部行为与状态不变量，而不是无必要地冻结某个内部函数的精确调用次数。

执行器则保证：源码来自不可变候选快照；额外探针属于明确版本的验证资产；测试输出写独立目录；必需测试确实运行且未被跳过。旧版本的 FAIL 必须能归因到目标反例，不能把环境故障当成缺陷证明。

R3 已允许独立裁决测试错误，这一点应保留。**正确的测试纠错必须能够恢复流程，否则“冻结测试”会变成冻结错误。**:chatgpt-content-reference{index="14"}

**验收**

“零测试执行”“全部 skip”“额外 Retry 才成功”“脏工作树冒充同 SHA”均不能形成通过证据；合法的测试纠错经版本化裁决后可以继续；同一有效反例在坏版本因目标断言失败、在新候选通过时能够准出。

这仍不能机械证明测试语义完全正确。控制器负责证据绑定，独立语义判断负责确认断言确实代表原目标。

### 4. 写入前原子记账不能单独保证崩溃后的幂等执行和硬时限

**类型：执行契约必须明确的保证边界；不是要求现在选定某种容器实现。**

**原文依据**

R4 要求在启动 Builder 前原子取得写入身份并登记预算；R5 要求持久 deadline 和恢复核验；安全边界又要求旧 writer 无法确认退出时不得发放新 writer。:chatgpt-content-reference{index="15"} :chatgpt-content-reference{index="16"}

**失败轨迹**

第一条轨迹是启动结果不明：

1. 控制器登记 `executionId=E` 并扣一次预算。
2. Builder 已启动。
3. 控制器在保存启动回执前崩溃。
4. 恢复后只看持久记录，无法判断应当补启动还是接管旧进程。

第二条轨迹是时限失去执行者：

1. Builder 正常运行。
2. 检查 deadline 的控制器退出。
3. Builder 或其子进程继续工作，但没有执行边界负责到期停止。

持久化一个 deadline 只能保留规则，**不能自动让失去监督的执行遵守规则**。而永久保留写锁虽然安全，也不等于能继续推进。

**最小修正**

把现有 bridge/runner 的启动契约明确为：

> 同一个 execution ID 的重复启动请求，返回同一个执行或其终态；不能再次启动一份新执行。

执行器还必须有独立于父控制器轮询的到期停止能力，并能识别、查询、终止本任务拥有的执行范围。具体采用已有 runner、隔离用户还是容器，可以留到实施阶段；**是否具备这项保证，不能留成含糊承诺。**

同链预算、分支唯一写许可和执行 intent 原子登记；执行器使用该 intent 启动。基础设施恢复沿用原执行身份，但经过有效验证失败后的再次源码修改，不能伪装成免费恢复。

无法确认旧执行退出时，正确行为仍是阻塞并展示待核实项，不能因为租约过期就假定进程消失。此时只能承诺“不再授权新的写入”，不能同时宣称“旧执行已停止、成本已封顶、流程可自动继续”。

**验收**

两个控制器竞争只得到一个 writer；启动前后任意崩溃都不重复派工；父控制器退出后，受支持的 runner 仍能落实执行期限；旧执行身份不明时拒绝新 writer；正常可识别的执行能够被接管，而不是所有恢复都永久阻塞。

### 5. 总时限没有为最终验收留出预算，会把正确候选也提前淘汰

**类型：交付率风险，不是安全门禁应当放宽的理由。**

**原文依据**

提案建议总时限两小时，同时保留最终五席完整审查。材料最后一次完整审查约为 38 分 45 秒。:chatgpt-content-reference{index="17"} :chatgpt-content-reference{index="18"}

**失败轨迹**

假设一个任务在第 105 分钟得到正确候选，只剩 15 分钟。若最终审查耗时接近材料最后一轮，即使实现已经正确，也无法在两小时内完成准出。

这里应当停止，不能降低门禁。但它说明：**固定总预算保证了终止，不保证预算被分配到能够完成交付的路径上。**

**最小修正**

保留一个总 deadline，同时提前设置“停止新增源码派工”的截止点，为必要验证、最终五席审查、发布核对和停止清理预留时间。

新派工前不仅检查“还剩几次”，还要检查“是否仍保留完成必要后续阶段的预算”。预留值需要按任务类型和历史阶段耗时校准，不能把一次 38 分钟观察直接当作通用常量。

诊断十五分钟也只是上限，不是到总时限后额外赠送的时间。预算已经耗尽时，应导出已有证据与明确阻塞原因，不能保证还能完成一次新的根因诊断。

**验收**

用模拟时钟验证：会侵占最终验收预留的新派工被拒绝；已合格候选能进入并完成最终验收；最终发现真实重大反例而预算不足时进入需要处理，不跳过审查、不自动追加，也不换链继续。

## 二、R1–R9 的保留、修改与合并建议

**不建议增加第十套机制。应减少独立状态来源，让现有要求共享合同、验收清单、执行记录和准出回执。**

| 要求 | 结论 | 最小调整 |
|---|---|---|
| **R1 原目标合同** | 保留、收缩 | 固定原请求、范围、不变量、可观察验收和策略引用。机械完整性检查不等于语义正确。预算引用同链记录，不重复维护。 |
| **R2 发现裁决** | 修改 | 裁决结果必须同时决定派工与门禁；不可变断言与可调整根因分组分开。 |
| **R3 验收资产** | 保留、补强 | 明确测试允许的刺激、真实失败原因和验证资产版本；支持有证据的测试纠错。 |

| **R6 进展与诊断** | 简化 | 以有效反例在有效修复后的重复失败触发诊断。建议删除“连续两次没有新增验收”这条独立自动停写规则，避免与证据补充混淆；其余空转由重试额度和总预算限制。 |
| **R7 交接任务卡** | 合并 | 作为 R1/R3/R5 的只读投影，不再形成一个需要单独同步的权威状态。 |
| **R8 独立证据准出** | 保留、修改 | 使用明确身份事实、可信预期策略和统一验收清单；未知不通过，合法证据也不能被原始文字重复否决。 |
| **R9 界面状态** | 保留、瘦身 | 展示已有状态及原因，不另建业务状态机；运行中断与业务结果分开。 |

这些调整对应提案已有的 R1–R9，不要求另建工程引擎。:chatgpt-content-reference{index="19"}

### 哪些必须机器强制，哪些不能交给机器“假装理解”

**必须机器强制：**身份一致、预算继承、唯一写许可、执行幂等、授权范围、证据来源与版本、必需责任覆盖、状态转移及发布条件。

**必须依赖语义裁决：**反例是否违反原目标、两个发现是否等价、是否属于范围内遗漏、测试是否证明目标、测试修订是否削弱验收。控制器保存和执行裁决，但不能通过字段齐全或 hash 一致来替代这些判断。

**可以合并或延后：**复杂根因自动聚类、独立任务卡存储、精细化 UI、多 adapter 同时铺开、缺数据时的精确 token 计费。格式纠错优先使用确定性结构处理；需要重新判断内容时，作为有预算的原席位重试，不再设一条反复重判的纠错循环。材料中的 17 条 correction 均未采纳，支持优先停止这种重复成本，但不支持据此估算节省金额。:chatgpt-content-reference{index="20"}

## 三、更小而完整的执行协议

### 1. 只保留四类权威数据

| 数据 | 内容 |
|---|---|
| **目标合同** | 原请求、目标版本、范围、不变量、准出策略与授权引用。 |
| **验收清单** | 断言版本、责任、测试/证据引用、原始 finding 映射、裁决结果。 |
| **执行记录** | chain、预算、execution ID、输入/输出候选、阶段、执行结果及恢复信息。 |
| **准出回执** | 候选、base、策略、证据引用、远端核验和检查时间。 |

任务卡、进度页、根因统计都从这四类数据生成。保留原始报告和日志，但不让它们绕过裁决直接决定下一次源码派工。

### 2. 状态转移

以下是**建议的 v2 路径**，不是对现有逐轮发布行为的静默修改。现有公开 review 入口缺少本地候选参数，必须补齐能力后才能采用。:chatgpt-content-reference{index="21"} :chatgpt-content-reference{index="22"}

| 状态 | 允许执行的工作 | 转移条件 |
|---|---|---|
| **准备** | 核对合同、PR、历史、授权、能力及验收清单 | 有已裁决缺陷且满足派工条件，进入实现；已有候选需补证，进入验证；信息不足则需要处理。 |
| **实现** | 一个受限 writer 执行一次已登记任务 | 形成固定候选后进入验证；无候选失败仍消耗本次派工预算，不自动免费重开。 |
| **验证** | 累计契约测试、必要现有检查、独立 Review/Verify | 全部通过进入最终审查；真实代码失败可申请下一次派工；证据缺口只补证；冲突或重复失败进入有界诊断。 |
| **最终审查** | 冻结的五席完整审查 | 责任覆盖和裁决均满足，进入发布；新发现先裁决，不直接转为修复命令。 |
| **发布与核对** | 可信发布入口执行条件更新并核验远端 | source、base、PR 状态及门禁均匹配，生成已准出回执；漂移或结果未知则需要处理。 |
| **需要处理／用户停止** | 保存证据、终止所属执行、说明恢复条件 | 只有具体阻塞已解除，且原链预算与授权仍有效，才允许续接。 |

“诊断”不必成为另一套工作流；它可以是验证阶段的一种限时只读执行。运行进程的 `interrupted` 则是执行状态，不应被混成“研发任务已经失败”或“用户已经停止”。

### 3. 四条必须明确的分支规则

**新发现。**范围内真实回归继续沿同链处理；范围外重大问题不自动修复，也不能靠“范围外”批准整个 PR。未证实假设进入有限验证，不直接消耗源码派工。现有 minor/nit 闭环要求不自行降低。:chatgpt-content-reference{index="23"} :chatgpt-content-reference{index="24"}

**证据冲突。**先确认是否针对同一候选、同一断言和同一测试版本。不同断言不是冲突；弃权不是反证；同一断言上的有效反例不能被多数通过票覆盖。

**预算与恢复。**没有生成 commit 的可写任务仍计预算；没有有效验证结果的任务不自动计为“同根因修复失败”。追加预算保留累计使用量，也不能自行解除已触发的诊断要求。:chatgpt-content-reference{index="25"}

**发布结果不明。**先读回远端。若已是候选且其他身份条件有效，补记核对结果，不再次发布；若已漂移，保留候选并阻塞；若旧发布仍可能在途，不盲目重发。这里应保证的是可核验、无覆盖的逻辑发布，而不是在所有网络故障下声称请求恰好只发送过一次。

候选测试和发布 hooks 的权限边界，原文已经写对，应原样保留并做运行时验收，不能把它们再列成“提案完全遗漏的安全问题”。:chatgpt-content-reference{index="26"}

## 四、怎样避免固定反例过拟合

**固定反例应当是累计下限，而不是正确性的完整定义。**

PR #128 可以先围绕材料已有的五类契约组织测试：身份隔离、durable 提交、恢复活性、Prompt 副作用、锁序与停机。它们是覆盖维度，不应直接宣称恰好对应五个独立根因。:chatgpt-content-reference{index="27"}

建议保留三个层次：

| 层次 | 作用 |
|---|---|
| **原始反例** | 保证已经确认的问题不会被遗忘或重新引入。 |
| **邻近交错与失败边界** | 检查同一不变量在检查前、提交中、提交后、补偿失败、释放占用等相邻路径上是否仍成立。 |
| **最终独立探索** | 允许最终五席发现尚未进入固定测试集的新问题。 |

每次修复重跑累计契约测试，独立审查重点检查 delta 与受影响路径；最终完整审查保留。这样减少的是重复发明同一反例的模型成本，而不是减少发现未知回归的责任。

对于恢复活性，还应写清环境前提。例如“存储最终恢复、runtime 保持 Ready 后应继续恢复”，与“存储永久失败也必须恢复成功”不是同一个要求。否则测试可能把不可能兑现的环境假设变成永久阻塞项。

## 五、如何校准“两次失败、三次派工、两小时”

**“同根因两次”适合作为转入诊断的启发式，不适合作为问题已被证明不可修复的结论。**

其计数至少应满足：确实针对同一冻结断言或经裁决的根因，确实执行过源码修复，并且后续有效验证仍给出反例。席位失败、格式失败、缺日志和环境故障不计入该次数，但仍消耗各自的时间与调用预算。

“三次派工、两小时”目前只能作为待试运行的 profile。附件主要是同一个 PR 的连续轨迹，并非多个独立任务的交付样本；各 review 墙钟、席位时长、实现耗时也不是同一统计口径，不能直接据此推导最优阈值。:chatgpt-content-reference{index="28"}

校准时先重建任务级数据：每次派工、验证、诊断和最终审查的耗时，是否产生有效关闭证据，是否出现新回归，以及最终是否交付。缺失数据保留 unknown。

随后在相近任务难度、相同准出标准和可比预算下比较策略。核心指标应是：

\[
\text{有效交付率}
=
\frac{\text{达到同等门禁且经后续独立检查仍有效的交付任务数}}
{\text{全部纳入比较的任务数}}.
\]

同时报告回归逃逸、总耗时、可观测成本及需要用户介入的比例。不能只比较成功任务，也不能把“更早进入需要处理”计成交付改善。

**历史事件重放能证明控制器按规则行动，不能证明换用新协议后模型必然写出更好的代码。**后者需要实际任务上的比较验证。

## 六、最小实施顺序与验收

| 阶段 | 最小交付 | 必须通过的正例与反例 |
|---|---|---|
| **1. 修正准出装配** | 策略、身份事实、coverage、重复判断一致 | 真实形状合法候选通过；未知 base/策略拒绝；弃权不制造假冲突；缺必需责任仍拒绝。 |
| **2. 接通验收清单与证据** | 断言版本、原反例、测试映射、裁决投影 | 合法测试纠错后可以继续；定义漂移不能覆盖旧证据；手写回执、错误刺激、零测试不能通过。 |
| **3. 接通全链执行边界** | 持久预算、原子授权、幂等 runner、隔离与恢复 | 两控制器仅一个 writer；崩溃前后不重复派工；旧 writer 不明拒绝续写；正常执行可恢复；候选代码不能修改控制面或取得发布权限。 |
| **4. 启用明确授权的 v2** | 本地固定候选终审、时间预留、受控发布与简化界面 | 合法候选能完成终审并交付；发布成功但回执丢失可核对恢复；远端漂移不覆盖；最终新反例不能绕过预算或门禁。 |

阶段 1–3 可以先用历史事件和模拟执行器验证，避免调用真实模型反复试错。**强隔离及执行停止能力未经运行时验收之前，不应对真实自动写入宣称“不可绕过”或“硬时限已经保证”。**

对于 PR #128 本身，下一步仍应是整理已有证据、固定恢复契约测试、明确状态机的所有权与补偿规则，而不是立即再启动一轮补丁加全量审查。但不必先把 67 条账本全部发展成复杂根因知识库：保留完整记录，建立必要的等价映射和验收断言即可。

## 七、修订后的精简协议摘要

> **一个原目标对应一条持久修复链。**控制器保存版本化目标合同、经裁决的验收清单、累计预算和执行记录。每次源码派工先原子取得写许可与预算，再由幂等、受监督的执行器启动。验证绑定不可变候选、测试版本和真实执行证据。缺证据只补证，事实冲突先裁决，重复有效失败触发有界诊断，不直接追加补丁。所有必要验收和最终五席审查通过后，可信发布入口核对远端并生成绑定候选、base、策略及时间的准出回执。预算耗尽、身份漂移或旧执行不明时，保留证据并进入需要处理；换任务、模型或父 Run 不重置历史。

仍需用户决定的主要是：

| 决策 | 需要确定的内容 |
|---|---|
| **是否启用新 v2 profile** | 派工上限、总时限、诊断上限，以及为最终验收预留多少预算；现有数值不能直接视为批准。 |
| **是否切换发布节奏** | 是否投入本地固定候选审查能力，改为完整终审后发布；能力未补齐前保留原流程。 |
| **不具备强执行隔离时怎么办** | 禁用强保证自动模式，还是允许明确标识的协作模式；不能静默降级。 |

在这些决定作出前，最终五席审查、现有 finding 准出要求、追加预算不清零，以及不得自动接受风险，继续作为既定约束。

**最终建议：先把“同一份裁决能决定派工与准出、同一个执行能够安全恢复、同一个合格候选确实能够通过”这三件事打通。固定预算负责停止无效循环；只有上述闭环与任务级交付数据，才能证明系统更会完成研发，而不只是更快停止。**
