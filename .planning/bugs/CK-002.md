## Bug 描述 (description)

When bufferEvent cannot fit an incoming non-terminal event even after coalescing (execution-registry.ts:130), it returns early before record.lastSeq = event.seq (line 137). Because emit allocates seq = record.lastSeq + 1 at line 174 BEFORE calling bufferEvent, and notify() at line 211 runs unconditionally, the dropped event is delivered to live follow() listeners with a seq that the next retained event reuses, violating the registry's strictly-increasing-seq contract. Independently reproduced: live listener seq [1,2,2] (Scenario A) and [1,2,3,3,3,3,3,3] (Scenario B, no pre-existing delta).

bufferEvent's coalesce-then-drop early return (line 130) skips the record.lastSeq = event.seq assignment (line 137), but emit allocates seq from lastSeq+1 (line 174) before the drop can happen, so a dropped event consumes a seq slot without advancing lastSeq and the next emit reuses the same seq for a different event

### P3 reviewer notes (accepted, not blocking)

The fix advances `lastSeq` on the drop path but the dropped event is never stored in `record.events`; `afterSeq` resume from a persisted snapshot therefore "skips" the dropped seq rather than replaying it. This matches the existing drop semantics (content dropped, seq consumed) and is the documented intent — a follow-up could record a lightweight tombstone marker if downstream ever needs to prove the seq gap was a drop and not data loss.
2. TC4/TC5/TC6 calibrate the cap by directly mutating `LIMITS.executionBufferBytes` via type assertion and rely on the per-delta byte math (`A*50` ~151 B, `B*400` ~501 B). If the event wire format or the framing overhead changes, the calibration constants may need re-tightening to keep both coalesce and the post-coalesce drop firing deterministically.
